برنامه‌نویسی پویا (Dynamic Programming) که به اختصار به آن دی‌پی می‌گوییم، یکی از مهم‌ترین تکنیک‌های طراحی الگوریتم است. ایده‌ی اصلی آن ساده است: اگر هنگام حل یک مسئله مجبور باشیم یک زیرمسئله‌ی یکسان را بارها حل کنیم، بهتر است جواب آن را فقط یک بار حساب کنیم و ذخیره کنیم تا دفعات بعد مستقیما از همان مقدار استفاده کنیم. به این ترتیب محاسبات تکراری حذف می‌شوند و معمولا زمان اجرا از نمایی به چندجمله‌ای کاهش پیدا می‌کند.

### چه زمانی از دی‌پی استفاده می‌کنیم؟

هر مسئله‌ای را نمی‌توان با دی‌پی حل کرد. معمولا وقتی سراغ این تکنیک می‌رویم که مسئله دو ویژگی داشته باشد:

1. **زیرمسئله‌های تکراری** (Overlapping Subproblems): هنگام حل مسئله، بارها به جواب یک زیرمسئله‌ی یکسان نیاز پیدا می‌کنیم.
2. **زیرساختار بهینه** (Optimal Substructure): جواب مسئله را می‌توان از روی جواب بهینه‌ی چند زیرمسئله‌ی کوچک‌تر ساخت.

برای مثال در دنباله‌ی فیبوناچی $F_n = F_{n-1} + F_{n-2}$ جواب هر جمله مستقیما از دو جمله‌ی قبلی ساخته می‌شود و همین زیرمسئله‌ها بارها تکرار می‌شوند؛ به همین دلیل فیبوناچی ساده‌ترین و معروف‌ترین مثال دی‌پی است.

!!! warning ""
    اگر هر زیرمسئله فقط یک بار محاسبه شود و تکراری در کار نباشد (مثل [مرج سورت](/Level1/sort/#_14))، ذخیره کردن جواب‌ها سودی ندارد و فقط حافظه مصرف می‌کند. قبل از استفاده از دی‌پی مطمئن شوید که واقعا زیرمسئله‌ی تکراری وجود دارد.

### مسئله‌ی فیبوناچی

در [بخش توابع بازگشتی](/Level1/recursive/) دیدیم که می‌توان فیبوناچی را مستقیما از روی تعریفش پیاده کرد:

```cpp linenums="1"

int fib(int n) {
    if (n <= 1)
        return n;
    return fib(n - 1) + fib(n - 2);
}
```

این کد ساده و طبیعی است اما مشکل بزرگی دارد. برای محاسبه‌ی `#!cpp fib(6)` درخت فراخوانی تقریبا به شکل زیر است:

```text
                fib(6)
               /      \
          fib(5)     fib(4)
          /    \      /   \
     fib(4) fib(3) fib(3) fib(2)
       ...
```

مقدار `#!cpp fib(4)` دو بار، `#!cpp fib(3)` سه بار و مقادیر کوچک‌تر حتی بیشتر محاسبه می‌شوند، در حالی که جوابشان همیشه یکسان است. این دقیقا همان زیرمسئله‌های تکراری است و باعث می‌شود تعداد فراخوانی‌ها از $\Theta(F_n)$ یعنی نمایی شود؛ مثلا `#!cpp fib(50)` میلیون‌ها فراخوانی ایجاد می‌کند.

مشکل این نیست که از بازگشت استفاده کرده‌ایم؛ مشکل این است که جواب یک زیرمسئله بارها حساب می‌شود. دو راه برای رفع آن داریم.

#### روش اول: ممویز کردن

ساده‌ترین راه این است که بعد از اولین محاسبه‌ی هر زیرمسئله، جواب را ذخیره کنیم و دفعات بعد همان را برگردانیم. به این کار ممویز کردن (Memoization) می‌گویند. آرایه‌ای مانند `#!cpp dp` می‌سازیم که همه‌ی خانه‌هایش در ابتدا $-1$ است؛ اولین باری که `#!cpp fib(n)` حساب شد، جواب را در `#!cpp dp[n]` می‌گذاریم.

```cpp linenums="1"

const int MAXN = 100000;

int dp[MAXN];

int fib(int n) {
    if (n <= 1)
        return n;
    if (dp[n] != -1) // (1)!
        return dp[n];
    return dp[n] = fib(n - 1) + fib(n - 2);
}

int main() {
    memset(dp, -1, sizeof(dp));
    cout << fib(40) << endl;
}
```

1. اگر این زیرمسئله قبلا حل شده باشد، بدون محاسبه جواب ذخیره‌شده را برمی‌گردانیم.

هر `#!cpp fib(i)` حداکثر یک بار واقعا محاسبه می‌شود، پس زمان از نمایی به $O(n)$ می‌رسد و حافظه هم (آرایه‌ی `#!cpp dp` و پشته‌ی بازگشت) $O(n)$ است. به این روش بالا به پایین (Top-Down) هم می‌گویند، چون از مسئله‌ی اصلی شروع می‌کنیم و به سمت زیرمسئله‌های کوچک‌تر می‌رویم.

#### روش دوم: پر کردن جدول

روش دیگر که در مسابقات بیشتر استفاده می‌شود این است که از کوچک‌ترین حالت‌ها شروع کنیم و کم‌کم جواب حالت‌های بزرگ‌تر را بسازیم. به این روش پایین به بالا (Bottom-Up) یا جدولی (Tabulation) می‌گویند. در فیبوناچی چون $F_0$ و $F_1$ را می‌دانیم، کافی است از روی آن‌ها $F_2$، بعد $F_3$ و همین‌طور تا $F_n$ را حساب کنیم.

```cpp linenums="1"

int fib(int n) {
    if (n <= 1)
        return n; // (1)!
    vector<int> dp(n + 1);
    dp[0] = 0;
    dp[1] = 1;
    for (int i = 2; i <= n; i++)
        dp[i] = dp[i - 1] + dp[i - 2];
    return dp[n];
}
```

1. بدون این خط، برای $n = 0$ آرایه فقط یک خانه دارد و نوشتن در `#!cpp dp[1]` خارج از آرایه است.

باز هم هر حالت دقیقا یک بار محاسبه می‌شود و زمان و حافظه $O(n)$ است، با این تفاوت که دیگر خبری از فراخوانی بازگشتی نیست و همه چیز در یک حلقه انجام می‌شود.

!!! warning ""
    اعداد فیبوناچی خیلی سریع بزرگ می‌شوند: $F_{47}$ دیگر در `#!cpp int` جا نمی‌شود و $F_{93}$ در `#!cpp long long`. در سوالات واقعی معمولا جواب را به پیمانه‌ی عددی مانند $10^9 + 7$ می‌خواهند و باید بعد از هر جمع باقی‌مانده بگیرید.

!!! tip "کدام روش بهتر است؟"
    از نظر پیچیدگی زمانی معمولا فرقی ندارند. روش جدولی هزینه‌ی فراخوانی بازگشتی ندارد و کنترل بیشتری روی ترتیب محاسبه و بهینه‌سازی حافظه می‌دهد؛ در عوض در بعضی مسائل نوشتن راه حل ممویزشده ساده‌تر و طبیعی‌تر است (و فقط حالت‌هایی که واقعا لازم‌اند حساب می‌شوند). انتخاب به ساختار مسئله بستگی دارد.

### مراحل حل یک مسئله‌ی دی‌پی

بیشتر مسائل دی‌پی با وجود تفاوت ظاهری، روند حل یکسانی دارند. به جای حفظ کردن فرمول هر مسئله، این چهار قدم را یاد بگیرید:

#### قدم اول: تعریف حالت

مهم‌ترین قدم، تعریف حالت (State) است: هر خانه‌ی آرایه‌ی `#!cpp dp` دقیقا چه چیزی را نگه می‌دارد؟ مثلا «`#!cpp dp[i]` جمله‌ی $i$ام فیبوناچی است»، «`#!cpp dp[i]` کمترین هزینه‌ی رسیدن به خانه‌ی $i$ است» یا «`#!cpp dp[i][j]` تعداد راه‌های رسیدن به خانه‌ی $(i, j)$ است». تا وقتی نتوانید این جمله را دقیق بیان کنید، سراغ کد نروید.

#### قدم دوم: رابطه‌ی انتقال

بعد از تعریف حالت باید مشخص کنیم جواب هر حالت از روی کدام حالت‌های کوچک‌تر به دست می‌آید. به این رابطه، رابطه‌ی انتقال (Transition) می‌گویند و معمولا سخت‌ترین قسمت حل است. مثلا:

$$dp[i] = dp[i-1] + dp[i-2], \qquad dp[i] = \max(dp[i-1],\ dp[i-2] + a_i), \qquad dp[i][j] = dp[i-1][j] + dp[i][j-1]$$

#### قدم سوم: حالت‌های پایه

رابطه‌ی انتقال همیشه به حالت‌های کوچک‌تر وابسته است، پس باید چند حالت اولیه را مستقیم مقداردهی کنیم تا محاسبات از آن‌ها شروع شود. در فیبوناچی $dp[0] = 0$ و $dp[1] = 1$ پایه هستند. اگر پایه اشتباه باشد، کل جدول اشتباه می‌شود.

#### قدم چهارم: ترتیب محاسبه

در روش جدولی باید حالت‌ها را طوری پیمایش کنیم که هنگام محاسبه‌ی هر حالت، همه‌ی حالت‌هایی که به آن‌ها نیاز دارد قبلا پر شده باشند. در فیبوناچی یعنی از کوچک به بزرگ؛ در مسائل دوبعدی ممکن است سطر به سطر یا به ترتیب دیگری باشد.

!!! danger "چهار سوال طلایی"
    تقریبا همه‌ی مسائل دی‌پی با پاسخ به این چهار سوال حل می‌شوند:

    1. هر خانه‌ی `#!cpp dp` چه معنایی دارد؟
    2. هر حالت از روی کدام حالت‌ها ساخته می‌شود؟
    3. حالت‌های پایه کدام‌اند؟
    4. جدول را با چه ترتیبی پر کنیم؟

### بهینه‌سازی حافظه

در بسیاری از مسائل، هر حالت فقط به چند حالت قبلی وابسته است و لازم نیست کل جدول را نگه داریم. در فیبوناچی هر مقدار فقط به دو مقدار قبلی نیاز دارد:

```cpp linenums="1"

int fib(int n) {
    if (n <= 1)
        return n;
    int a = 0, b = 1;
    for (int i = 2; i <= n; i++) {
        int c = a + b;
        a = b;
        b = c;
    }
    return b;
}
```

زمان همچنان $O(n)$ است ولی حافظه از $O(n)$ به $O(1)$ رسیده است. بعد از طراحی هر راه حل دی‌پی، بررسی کنید که آیا واقعا به کل جدول نیاز دارید یا چند حالت آخر کافی است (نمونه‌ی دیگری از این کار را در [کوله‌پشتی](/Level2/knapsack/) می‌بینید).

### دی‌پی یک‌بعدی

وقتی حالت مسئله فقط با یک عدد (شماره‌ی خانه، شماره‌ی روز، طول یک رشته و…) مشخص می‌شود، جواب‌ها را در یک آرایه‌ی یک‌بعدی نگه می‌داریم.

#### مسئله

می‌خواهیم از خانه‌ی $0$ به خانه‌ی $n$ برسیم و در هر حرکت می‌توانیم یک یا دو خانه جلو برویم. چند مسیر مختلف وجود دارد؟

#### راه حل

اگر `#!cpp dp[i]` تعداد راه‌های رسیدن به خانه‌ی $i$ باشد، آخرین حرکت یا از $i-1$ آمده یا از $i-2$؛ پس $dp[i] = dp[i-1] + dp[i-2]$ که دقیقا رابطه‌ی فیبوناچی است، با پایه‌ی $dp[0] = dp[1] = 1$.

```cpp linenums="1"

long long countWays(int n) {
    vector<long long> dp(n + 1);
    dp[0] = 1;
    dp[1] = 1;
    for (int i = 2; i <= n; i++)
        dp[i] = dp[i - 1] + dp[i - 2];
    return dp[n];
}
```

البته همه‌ی دی‌پی‌های یک‌بعدی به جمع دو حالت قبلی ختم نمی‌شوند. اگر ایستادن روی خانه‌ی $i$ هزینه‌ی $cost_i$ داشته باشد و کمترین هزینه‌ی رسیدن به $n$ را بخواهیم، رابطه $dp[i] = \min(dp[i-1], dp[i-2]) + cost_i$ می‌شود؛ یا اگر بیشترین امتیاز را بخواهیم ممکن است رابطه‌ای مانند $dp[i] = \max(dp[i-1], dp[i-2] + a_i)$ داشته باشیم. مهم نیست عملیات انتقال جمع، کمینه یا بیشینه باشد؛ مهم این است که جواب هر حالت از روی چند حالت کوچک‌تر ساخته شود.

### دی‌پی دوبعدی

گاهی یک متغیر برای توصیف حالت کافی نیست و به دو متغیر نیاز داریم؛ در این صورت جدولی دوبعدی می‌سازیم که هر خانه‌اش جواب یک زیرمسئله است.

#### مسئله

روی جدولی $n \times m$ از خانه‌ی بالا-چپ شروع می‌کنیم و فقط می‌توانیم به راست یا پایین برویم. به چند طریق می‌توان به خانه‌ی پایین-راست رسید؟

#### راه حل

اگر `#!cpp dp[i][j]` تعداد راه‌های رسیدن به خانه‌ی $(i, j)$ باشد، آخرین حرکت یا از خانه‌ی بالایی بوده یا از خانه‌ی سمت چپ:

$$dp[i][j] = dp[i-1][j] + dp[i][j-1]$$

خانه‌ی شروع را $1$ می‌گذاریم و جدول را سطر به سطر پر می‌کنیم.

```cpp linenums="1"

vector<vector<long long>> dp(n, vector<long long>(m, 0));
dp[0][0] = 1;

for (int i = 0; i < n; i++) {
    for (int j = 0; j < m; j++) {
        if (i > 0) dp[i][j] += dp[i - 1][j];
        if (j > 0) dp[i][j] += dp[i][j - 1];
    }
}
```

هر خانه در $O(1)$ محاسبه می‌شود، پس زمان و حافظه $O(nm)$ است. نمونه‌های دیگری از دی‌پی دوبعدی را در [کوله‌پشتی](/Level2/knapsack/)، [LIS و LCS](/Level2/lis_lcs/) و [دی‌پی بازه‌ای](/Level2/dplr/) می‌بینید. در مباحث پیشرفته‌تر دی‌پی سه‌بعدی و بیشتر هم داریم، اما ایده همان است و فقط تعداد پارامترهای حالت بیشتر می‌شود.

### اشتباهات رایج

+ **تعریف مبهم حالت:** اگر معنای `#!cpp dp[i]` دقیق نباشد، نوشتن رابطه‌ی انتقال تقریبا غیرممکن است.
+ **فراموش کردن حالت‌های پایه:** یک پایه‌ی اشتباه، کل جدول را خراب می‌کند.
+ **ترتیب اشتباه محاسبه:** اگر `#!cpp dp[i]` به `#!cpp dp[i-1]` وابسته باشد ولی جدول را از آخر پر کنیم، هنگام محاسبه مقدار لازم هنوز آماده نیست.
+ **حافظه‌ی بی‌دلیل:** وقتی فقط چند حالت قبلی لازم است، نگه داشتن کل جدول اتلاف حافظه است.
+ **نوع داده‌ی نامناسب:** تعداد حالت‌ها یا جواب معمولا بزرگ می‌شود؛ از `#!cpp long long` استفاده کنید یا اگر مسئله خواسته، در هر مرحله به پیمانه‌ی عددی مانند $10^9 + 7$ حساب کنید.

### چگونه دی‌پی را تشخیص دهیم؟

قانون قطعی وجود ندارد، اما چند نشانه کمک می‌کند. اگر مسئله **بهترین جواب** (کمترین هزینه، بیشترین امتیاز، بلندترین دنباله) یا **تعداد راه‌ها** یا **امکان‌پذیر بودن** یک کار را می‌خواهد و جواب هر حالت از روی چند حالت کوچک‌تر به دست می‌آید، احتمالا با یک مسئله‌ی دی‌پی روبه‌رو هستید. همچنین اگر در یک راه حل بازگشتی دیدید تابعی با ورودی یکسان بارها صدا زده می‌شود، همان‌جا می‌توان با ممویز کردن یا پر کردن جدول آن را بهینه کرد.

!!! tip "تفاوت با تقسیم و حل"
    در [تقسیم و حل](/Level1/divide/) هم مسئله به زیرمسئله‌های کوچک‌تر شکسته می‌شود، اما آن زیرمسئله‌ها معمولا مستقل‌اند و هر کدام فقط یک بار حل می‌شوند (مثل دو نیمه‌ی آرایه در مرج سورت). در دی‌پی زیرمسئله‌ها با هم هم‌پوشانی دارند و اگر جوابشان را ذخیره نکنیم، بارها حل می‌شوند.

در پایان یادتان باشد که دی‌پی مجموعه‌ای از فرمول‌های حفظ‌کردنی نیست؛ روشی است برای شکستن یک مسئله‌ی بزرگ به زیرمسئله‌های کوچک‌تر و استفاده‌ی دوباره از جواب آن‌ها. هرچه مسئله‌ی بیشتری حل کنید، سریع‌تر حالت مناسب را پیدا می‌کنید.
